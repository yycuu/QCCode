# QCCode V1 Specification

Status: implementation specification for protocol version 1.0.

QCCode is an independent circular binary visual-code protocol. It does not use QR, Aztec, Data Matrix, or Apple App Clip Code layouts or wire formats. Normative terms MUST, MUST NOT, SHOULD, and MAY have their RFC 2119 meanings.

## Architecture and security boundary

The server converts an application payload to bytes, serializes a canonical envelope, and signs it with Ed25519. A display client receives the complete signed envelope and only performs visual encoding. Server private keys MUST NOT be distributed to display or scanner clients.

The scanner MUST preserve and submit the original signed envelope bytes. A server MUST parse, verify, and apply policy itself. Client claims such as `valid: true` are never authoritative.

Digital signatures prevent undetected forgery and modification. They do not prevent a valid image from being copied. Single-use behavior therefore requires expiration, random message and nonce values, and atomic server-side redemption.

## Envelope

All integers are unsigned and big-endian. Byte offsets are zero-based.

| Offset | Size | Field | V1 value or rule |
|---:|---:|---|---|
| 0 | 4 | Magic | `C7 51 43 01` |
| 4 | 1 | Version | major in high nibble, minor in low; V1.0 is `10` |
| 5 | 1 | Mode | INLINE `01`, REFERENCE `02`, CHALLENGE `03` |
| 6 | 2 | Flags | bitset below |
| 8 | 1 | Signature algorithm | Ed25519 `01` |
| 9 | 16 | Issuer ID | opaque 128-bit value |
| 25 | 4 | Key ID | unsigned integer |
| 29 | 2 | Message type | application registry value |
| 31 | 16 | Message ID | CSPRNG output |
| 47 | 8 | Issued at | Unix UTC seconds |
| 55 | 8 | Expires at | Unix UTC seconds |
| 63 | 16 | Nonce | CSPRNG output |
| 79 | 2 | Payload length | N |
| 81 | N | Payload | opaque bytes at the protocol layer |
| 81+N | 64 | Signature | Ed25519 `R || S` |

The total size is `145 + N` bytes. The signature input is exactly bytes `[0, 81+N)`. Parsing MUST consume the whole input and reject trailing data.

Flags are: bit 0 single-use, bit 1 server resolution required, bit 2 explicit user confirmation required, and bit 3 auditable. Bits 4 through 15 MUST be zero. REFERENCE requires bit 1. CHALLENGE requires bits 0, 1, and 2.

REFERENCE payload is a 2-byte resource type followed by a 16-byte random resource ID. CHALLENGE payload is a 2-byte challenge type, 16-byte random challenge ID, and 32-byte SHA-256 context hash; an all-zero hash means absent. INLINE is application-defined bytes.

No JSON representation participates in canonicalization. Implementations MUST verify the received byte slice and MUST NOT parse and reserialize before verification.

## Visual frame and CRC

RS source data consists of an 8-byte frame header, the envelope, a 4-byte CRC, and zero padding:

| Offset | Size | Field |
|---:|---:|---|
| 0 | 2 | magic `A7 3C` |
| 2 | 1 | visual version `01` |
| 3 | 1 | layout ID: C1 `01`, C2 `02`, C3 `03` |
| 4 | 1 | ECC ID: RS(255,191) `01` |
| 5 | 1 | mask ID 0 through 7 |
| 6 | 2 | envelope length |
| 8 | N | signed envelope |
| 8+N | 4 | CRC-32C |
| 12+N | P | zero padding |

CRC-32C covers bytes `[0,8+N)`. It uses the Castagnoli polynomial `0x1EDC6F41`, reflected polynomial `0x82F63B78`, initial value `FFFFFFFF`, reflected input/output, and final XOR `FFFFFFFF`.

## Error correction and layouts

Every block uses systematic RS(255,191) over GF(256), primitive polynomial `0x11D`, generator 2, first consecutive root 0, and 64 parity bytes. Correction is valid when `2e+s <= 64` for unknown errors `e` and known erasures `s`.

| Layout | Blocks | Data rings | Slots | Raw bytes | RS source | Max envelope |
|---|---:|---:|---:|---:|---:|---:|
| C1 | 1 | 6 | 1020 × 2 bits | 255 | 191 | 179 |
| C2 | 2 | 9 | 2040 × 2 bits | 510 | 382 | 370 |
| C3 | 3 | 12 | 3060 × 2 bits | 765 | 573 | 561 |

Ring slot counts, inner to outer:

- C1: `140,152,164,176,188,200`
- C2: `194,202,210,218,226,234,242,250,264`
- C3: `222,228,234,240,246,252,258,264,270,276,282,288`

Frame source byte `i` goes to block `i mod blockCount`, position `floor(i/blockCount)`. Encoded visual byte `q` is taken from block `q mod blockCount`, position `floor(q/blockCount)`. Bytes expand most-significant bit first.

Two consecutive logical bits form a quaternary symbol, most-significant bit first. Logical symbol `p` maps to ring-major physical index `(a*p) mod S`, where `(a,S)` is C1 `(509,1020)`, C2 `(1031,2040)`, or C3 `(1543,3060)`. Each pair is coprime, so the mapping is invertible.

## Orientation and bootstrap

The 63-slot orientation ring is generated by `s[0..5]=1`, `s[n+6]=s[n+1] XOR s[n]`:

```text
111111000001000011000101001111010001110010010110111011001101010
```

Decoders correlate all cyclic rotations in both directions. They reject results whose normalized best score is below 0.70 or whose best-to-second distinct rotation margin is below 0.16. Reverse correlation identifies mirroring.

The 64-slot bootstrap ring contains two copies of a 32-bit codeword. Its 16 message bits are marker `10110` (5), layout (2), ECC (2), mask (3), and four zero reserved bits. It uses systematic BCH(31,16,7) with generator `x^15+x^11+x^10+x^9+x^8+x^7+x^5+x^3+x^2+x+1`, followed by one even parity bit.

## Masks

Only data slots are masked. For zero-based ring `r` and slot `s`, mask predicates are:

```text
M0=0
M1=(r+s)%2
M2=(s%3==0)
M3=((2r+s)%5<2)
M4=(r*s+r+s)%2
M5=popcount((r+1)*(s+1))%2
M6=(floor(s/3)+r)%2
M7=((s*s+3r+s)%7<3)
```

For mask zero the quaternary mask value is zero. For mask `m` from 1 through 7, the two-bit mask symbol is `Mm(r,s) | (M(((m+2) mod 7)+1)(r+1,s) << 1)`. The visual symbol is the two-bit data symbol XOR this mask symbol. Bootstrap and frame mask IDs MUST agree.

## Geometry

With guard outer radius 1.0, quiet zone extends to at least 1.12. Guard ring occupies radii 0.94–1.00, orientation 0.86–0.92, bootstrap 0.79–0.84, and the data band ends at 0.77 so its outer markers visually meet the bootstrap band. C1/C2/C3 center radii are 0.38, 0.34, and 0.30. Data markers fill their radial band after a small ring gap so each data ring matches the guard ring weight. The data band and center sit on a pale neutral background, default `#F1F3F2`, which is also the quaternary zero level.

The center carries no protocol, orientation, or ECC data. `center.mode=none` leaves the pale background visible. `center.mode=logo` may render an image inside at most 82% of the layout's center radius. Renderers must clip Canvas logos to that circle and must not allow a logo to overlap the innermost data ring. Decoders never sample the center.

Each data slot is a radially oriented ellipse filling its radial band, matching the guard ring weight. The tangential size is uniform across all data rings at 90% of the outermost ring's slot pitch, so inner and outer marks share one size. Each slot carries two bits using four ordered luminance states: background `00`, subtle light gray `01`, medium gray `10`, and black `11`. The default palette is `#F1F3F2`, `#C6CCC8`, `#737A76`, and `#000000`; the subtle first level reduces visual clutter while remaining separable by luminance. Custom palettes must remain strictly ordered by relative luminance with at least 0.06 luminance separation between adjacent levels. A decoder classifies levels from calibrated luminance clusters and marks low-confidence samples as erasures. Orientation and Bootstrap remain logically binary; their zero slots may be rendered with the standard pale calibration color `#DCE3DE`, which must remain on the background side of the binary threshold.

## Sparse S1 layout (visual version 2)

S1 renders the data area with the same sparse, guard-weight dash marks as the Orientation and Bootstrap rings. Its Bootstrap uses the version-2 preamble `0b10111` with layout id 1, so V1 decoders reject it cleanly. S1 has six data rings holding `[40, 48, 55, 61, 68, 72]` slots for 344 quaternary slots total, packed into one shortened RS(86,54) codeword: 54 data bytes and 32 parity bytes. The frame is the 48-byte bearer envelope followed by its CRC-32C and two zero padding bytes.

Each slot renders as a rounded-cap arc spanning 16% of its angular pitch with a stroke width equal to its radial band, so the marks match the guard ring weight. Slot pitch stays at or above the mark width, which keeps slot-center sampling unambiguous.

The S1 bearer envelope is exactly 48 bytes: magic `0xc4 0x02`, mode `0x02` (REFERENCE), flags, uint16 message type, 8-byte issuer id, 12-byte message id, uint32 issued-at and expires-at, uint16 resource type, and 12-byte resource id. It carries no signature: 96-bit resource ids are unguessable bearer secrets verified server-side with atomic single-use redemption. V1 signed layouts are unchanged and remain the offline-verifiable format.

## Server policy

Key lookup uses `(issuerId,keyId)`. New messages use the current key; previous keys may verify messages within their stated lifetime; revoked keys fail. Offline verification is possible only with a cached trusted key.

Single-use redemption MUST atomically claim `(issuerId,messageId)` before performing the protected operation. Implementations SHOULD also detect nonce reuse. Database adapters use a transaction and unique constraint. Redis adapters use one atomic script or `SET NX` plus a durable idempotent business workflow.

V1 provides authenticity, integrity, visual error recovery, and online replay control. It does not provide payload confidentiality, anonymous credentials, zero-knowledge proofs, post-quantum signatures, multisignatures, blockchain integration, or NFC.
